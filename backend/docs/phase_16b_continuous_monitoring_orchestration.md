# AQUILA Phase 16B — Continuous Monitoring & Event Orchestration

## 1. Architecture
Phase 16B introduces the foundational orchestration layer for AQUILA's automated continuous maritime monitoring. It shifts AQUILA from a purely manual tool to a reactive intelligence system. The orchestrator listens for `NewSceneEvent` objects (generated by CDSE subscriptions/polling) and transitions them through a deterministic forensic pipeline.

### MVP Infrastructure Decision
**In-Memory Orchestration (`asyncio` + `InMemoryJobRepository`)**
For Phase 16B, we use a lightweight, in-memory orchestration loop running as a FastAPI background worker (`OrchestrationWorker`).
**Limitations of this MVP:**
- **Volatility**: Process restart loses all in-memory jobs.
- **Concurrency**: Multiple API instances do not share job state.
- **Worker Lifecycle**: Tied directly to the FastAPI application process.
- **Scaling**: No durable queue or distributed locking.

This architecture explicitly isolates state transitions and idempotency so that in Phase 16C/17, it can be swapped for a persistent `FirebaseJobRepository` and `Celery`/`Cloud Tasks` worker *without rewriting the scientific pipeline logic*.

## 2. Event Flow
1. **CDSE Discovery** emits a `NewSceneEvent`.
2. **Ingestion**: The Orchestrator creates a `MonitoringJob`.
3. **Execution**: The async worker polls `QUEUED` jobs.
4. **Pipeline**: The orchestrator triggers satellite processing, candidate detection, and SVM classification.
5. **Trigger**: If candidates match the `InvestigationTriggerPolicy` (e.g., `OIL_LIKE`), an automated `Investigation` is created.
6. **Enrichment**: Open-Meteo, OpenDrift, and GFW AIS are queried.
7. **Attribution**: Evidence is fused and attributed.
8. **Resolution**: The job reaches `REPORT_READY` (or `RESOLVED` if no interesting anomaly).

## 3. State Machine
Jobs transition through an explicit Enum (`JobStatus`):
`DISCOVERED` → `QUEUED` → `RETRIEVING` → `PROCESSING` → `CANDIDATES_FOUND` → `CLASSIFYING` → `INVESTIGATION_CREATED` → `ENVIRONMENT` → `DRIFT` → `VESSEL_EVIDENCE` → `ATTRIBUTION` → `REPORT_READY`.

Non-interesting anomalies bypass investigation and jump to `RESOLVED`.
Transient failures enter `RETRY_WAIT`. Permanent/Max retry failures become `FAILED`.

## 4. Idempotency Strategy
- **Job Creation**: Deduplicated using a combination of `product_id` and `monitoring_zone_id`.
- **Investigation Creation**: Deduplicated using a deterministic anomaly fingerprint: `product_id + monitoring_zone_id + anomaly_id`. This allows multiple distinct anomalies in the same scene to spawn distinct investigations without duplicating the same anomaly if a scene event is re-ingested.

## 5. Retry Strategy
- **Bounded Backoff**: Transient exceptions move the job to `RETRY_WAIT`.
- **Retry Delay**: `(2 ^ retry_count) * 15 seconds`.
- **Max Retries**: Default is 3. Exceeding this moves the job to `FAILED`.

## 6. Monitoring Zones
Jobs are intrinsically tied to a `MonitoringZone`. A single satellite product intersecting multiple zones will generate independent `MonitoringJob`s, preserving isolation for different mission parameters.

## 7. Automatic vs Manual Investigations
- Manual investigations retain `creation_mode = "MANUAL"`.
- Orchestrator-spawned investigations set `creation_mode = "AUTOMATIC_MONITORING"`.
- Frontend workflows remain completely decoupled from the orchestrator.

## 8. Look-alike Handling
Anomalies classified as `LOOKALIKE` do not trigger forensic investigations. However, they are NOT discarded. The job transitions to `RESOLVED`, preserving the classification record in the job state for auditing and model retraining.

## 9. GFW Unavailable Behavior
If `GFW_API_TOKEN` is missing, the `GFWAISProvider` raises an exception. The orchestrator catches this, marks the vessel evidence as `UNAVAILABLE`, and proceeds to Attribution. No fake or mock data is injected into the production pipeline.

## 10. Environmental/Drift Failure Behavior
- **Open-Meteo**: Network failures are caught; environment marked `UNAVAILABLE`.
- **OpenDrift**: Timeouts or failures are caught; drift marked explicitly as `FAILED`. `DEMO_MOCK` is never silently substituted.

## 11. Provenance
Every job tracks `provenance_references` (e.g., `ENV:UNAVAILABLE`, `GFW:UNAVAILABLE`). The attribution engine respects `UNAVAILABLE` evidence without treating it as neutral.

## 12. Current Limitations
- In-memory persistence is volatile.
- No real-time frontend updates for orchestration progress.
- No external alert notifications (e.g., Email/Slack) upon `REPORT_READY`.

## 13. Exact Next Phase Recommendation
**Phase 16C Recommendation:**
Integrate Firebase to persist `MonitoringJob`, `MonitoringZone`, and `Investigation` state. Transition the `InMemoryJobRepository` to a `FirebaseJobRepository`. This will resolve the volatility limitation and prepare the system for durable Celery/Cloud Tasks workers and real-time frontend subscriptions.
